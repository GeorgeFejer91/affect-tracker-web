# Experimental remote Flubber state

This is the normative contract for the explicit browser-neutral Flubber transport used by browser endpoints and the Tauri settings WebView's Party adapter. It is a narrow network exception to the local-first default, not a physiology transport, remote-recording service, native Quest feature, LAN service, or general integration API.

The latest attended evidence and open physical gate are recorded in [`67-REMOTE-FLUBBER-QUALIFICATION-2026-08-25.md`](./67-REMOTE-FLUBBER-QUALIFICATION-2026-08-25.md).

## Product and privacy boundary

- The desktop browser exposes **Broadcast this to VR / remote interface**, the Meta Quest WebXR page exposes **Use incoming signal**, and Affect Tracker Desktop exposes **Host Party and scan** plus **Broadcast desktop Flubber** in its settings window. Loading any endpoint constructs no VDO.Ninja client and makes no connection; every page/app load requires a fresh exact button press.
- On the main Ground Control page, ordinary JSON/live broadcast and scan obey a strict sender-or-receiver gate. Starting or retaining any ordinary sender prevents ordinary receiving, and starting or retaining any ordinary scanner/receiver prevents ordinary sending. Universe is a separately named paired duplex role. Party does not relax the ordinary role gate: an invited ordinary broadcaster may receive only the bounded aggregate Party-scene reply on the same already-open data channel, as specified in `69-EXPERIMENTAL-FLUBBER-COLLABORATION.md`; it does not become an ordinary scanner or Party host.
- The desktop Broadcast gesture also opens the existing browser-owned floating Flubber and requests a renewable screen wake lock. Its `requestAnimationFrame` becomes the owner of smoothing, coordinate offers, and normalized placement offers, so covering the main Chrome window does not background the sender loop. If that helper is closed or displaced while broadcasting, the page immediately warns that low-latency foreground mode is degraded and exposes **Restore low-latency foreground mode**; this user-gesture path recreates the helper and wake lock without changing the public source. Stop immediately enters a non-broadcasting phase, cancels changed-value and heartbeat scheduling, closes every opened data channel, and only then awaits VDO signaling teardown; it releases the lock and closes only a helper opened by Broadcast. Manually opened Picture-in-Picture retains its normal independent lifecycle. If the helper is unsupported or blocked, keep the main tab foreground for reliable low latency.
- The browser sender offers the final smoothed `currentX/currentY` pair and the displayed Flubber center normalized over its movable viewport range as one timestamped state operation immediately before rendering. The Tauri broadcaster offers the Rust runtime's authoritative displayed `currentX/currentY` snapshot and a session-only desktop-stage placement; it never uses incoming data as native input. In ordinary transport neither endpoint transmits raw pointer events or a pointer trajectory, ECG, RR, heart rate, a metric name or value, timestamps, participant identity, visual settings, animation phase, CSV rows, or any other study data. Only after a Party host explicitly invites this source may the host return the bounded public aggregate scene described in `69-EXPERIMENTAL-FLUBBER-COLLABORATION.md`.
- Sources retain fresh per-session random transport suffixes with prefix `aft_flubber_`. WebXR-only sources without an operator name are shown as labels such as `Source AB12 CD34`. Ground Control adds a bounded sanitized operator name token before the random suffix so VDO.Ninja room listings can show the name before peer connection; the exact display label is also supplied as connection metadata, is not part of either wire packet, and must not contain a participant identifier. IDs, selections, coordinates, placements, and remote state are not persisted. The shared discovery room `affect_tracker_flubber_v1` is intentionally public; any room listener may receive the arbitrary coordinate and normalized-placement values.
- VDO.Ninja provides third-party signaling/STUN/TURN infrastructure. A connection requires internet signaling even when WebRTC negotiates a local peer-to-peer path. Peers may learn each other's IP addresses; TURN relay paths may increase latency; the hosted service has no project availability guarantee.
- The official SDK v1.5.5 distribution, corresponding readable source, MPL-2.0 license, provenance, and fixed hashes are checked into `site/vendor/vdoninja/1.5.5/`. Pages load the local minified file and use no SDK CDN; the desktop Vite build copies that same pinned directory into the packaged WebView rather than fetching another SDK.
- For attended relay qualification only, `?remote-force-turn=1` on each endpoint passes the official SDK's documented `forceTURN` option when that endpoint's explicit remote button constructs the client. The request is visible in route status, is never persisted, and creates no page-load connection. A run still requires independent peer-quality readback of `TURN relay`; the query flag alone is not route evidence.

## Transport and wire contract

- `site/src/flubber-remote.js` is the browser-neutral authority for discovery, lifecycle, packet codec, unsigned sequencing, rate control, heartbeat, staleness, route diagnostics, backpressure, injectable SDK/timer adapters, and constrained protocol-specific room/prefix/channel/label options used by Universe. Its default options remain the ordinary live-FLUBBER contract below.
- Use VDO.Ninja data-only publisher/viewer connections. Do not request a microphone, audio track, camera, media permission, popup, clipboard, keyboard, code entry, QR scanner, custom bridge server, or WebSocket data fallback.
- Join public room `affect_tracker_flubber_v1`. Each listener gets one required custom channel, `flubberxyv1`, using `ordered: false` and `maxRetransmits: 0`. Both affect and placement packets travel on this channel, so a successful affect connection also proves a path exists for drag synchronization. New receivers additionally accept the former optional `flubberpositionv1` channel from already-cached senders during the transition; new senders do not open it.
- Every affect packet is exactly 12 bytes, little-endian: `uint32 sequence`, `float32 currentX`, then `float32 currentY`. Coordinates must be finite and are clamped to `[-1,1]`. Every placement packet is exactly 16 bytes, little-endian: the four-byte ASCII magic `FVP1`, `uint32 sequence`, `float32 viewportX`, then `float32 viewportY`; placement components must be finite and are clamped to `[0,1]`. Each packet type owns its own unsigned sequence. Receivers reject any other length or magic, non-finite value, duplicate sequence, or value that is not newer under unsigned half-range ordering, including across wraparound. An older receiver safely ignores the unfamiliar 16-byte placement packet and continues reading the unchanged 12-byte affect packets.
- The same RTC data channel is technically duplex. Binary payloads retain the codecs above. A Party receiver may send one validated UTF-8 aggregate-scene string back to an invited broadcaster; generic auxiliary strings are capped at 16 KiB by `flubber-remote.js`, while the Party codec applies the stricter 8 KiB bound. Strings dispatch separately and never enter affect/placement decoding or liveness. The sender uses best-effort zero-backlog delivery, so Party replies cannot accumulate behind live state.
- Changed values of either packet type use an ideal 60 Hz deadline with a five-millisecond bounded early tolerance and at least 11.67 ms between changed sends. Advancing the ideal deadline instead of resetting it from each slightly-early Chrome frame prevents ordinary animation jitter from halving delivery cadence; the bounded debt is repaid so sustained high-rate callers remain limited to 60 Hz over time. Affect and placement are offered with one monotonic timestamp so they may be emitted as an adjacent pair despite the channel's latest-state backpressure. The latest affect and placement states are repeated on the 100 ms heartbeat so a lost final drag packet can recover, but only affect receipt owns liveness. A new listener receives the latest available affect pair and placement immediately. If the channel already has queued bytes before that state batch, the update is discarded for that listener; only its newest state is eligible once the queue clears.

## Receiver ownership

- Browser receivers treat normalized placement as relative movement, not absolute cross-device coordinates. The first placement frame anchors the sender's current point to the receiver's current local Flubber point, so connecting never jumps the receiving object. Later sender displacement is added to that local normalized anchor and clamped to `[0,1]`; a movement across 20% of the sender's movable span therefore traverses 20% of a differently sized receiver's movable span in the same direction. A local drag or arrow-key move on the receiving Flubber establishes a new local/sender anchor, retaining independent placement while subsequent remote movement continues. Placement frames never establish, recover, or extend affect liveness.
- The phone controller's upper canonical SVG is a direct manipulation surface for this placement. It must be grabbed as the existing object, uses pointer capture, clamps within its pane, maps to the main widget's normalized movable range, and supports arrow keys. The lower 2D field continues to own affect X/Y only.
- Quest discovery waits approximately 300 ms. One source is selected automatically; multiple sources produce large tap/controller-ray buttons. The selected source never changes automatically during immersive WebXR.
- Quest/WebXR deliberately ignores the optional normalized 2D viewport placement because its Flubber uses head/controller/world-relative 3D rigging. The required affect channel and all existing XR ownership semantics are unchanged.
- Incoming mode and direct Quest Polar acquisition are mutually exclusive. Enabling incoming mode disconnects an active H10 while retaining its page-memory mappings. Remote mode owns both axes, ignores thumbstick movement and reset, and bypasses local smoothing by writing every accepted pair to both `targetX/Y` and `currentX/Y` for the next XR frame. Pause remains the study's whole-session control.
- Immersive entry is blocked while incoming mode is enabled without a valid live packet. Leaving incoming mode is explicit and releases both axes to the existing Quest controller/direct-Polar path.
- Apply every accepted pair immediately; do not add a coordinate delay buffer. At two seconds without a valid packet, retain the last coordinates and show `REMOTE • SIGNAL LOST — HOLDING` in the in-world HUD. This grace exceeds the roughly one-second packet-delivery batching measured when Meta Quest deprioritizes a visible browser panel. A fully backgrounded ordinary browser tab may defer both data-channel message tasks and the stale timer for substantially longer; timestamps are intentionally absent, so queued packets cannot be distinguished from fresh packets in that unsupported scheduling state. Complete connection before immersive entry and keep the receiver in foreground immersive WebXR for the bounded low-latency workflow. After stale entry, apply returning coordinates immediately but require three consecutive valid frames before the UI/HUD reports recovery; an isolated intermittent frame therefore cannot flap the status. Source loss never falls through to controller or Polar input.
- Browser desktop and Quest expose idle, discovery/selection, connecting, live, stale, direct/relay, foreground mode, and error information with accessible status announcements. Tauri Party exposes idle, radar/broadcasting, participant, per-guest phase/route, returned-scene, and error state in the settings window. Quest also shows bounded receiver-local frame count and gap timing plus whether it is an ordinary browser panel, foreground immersive WebXR, system-overlay-blurred XR, or hidden XR. Incoming mode requests and renews a screen wake lock, while the immersive XR session is the standards-based foreground/lowest-latency path. Neither API can override Meta OS scheduling while another system or spatial surface owns focus. Quest source controls require no typing and must remain usable with controller rays before immersive entry.

- A data-channel close or selected-source departure records its disconnected edge immediately but uses the same two-second packet-age grace before changing the visible state to stale. A replacement channel that produces a valid frame inside the grace therefore does not flash the UI or HUD live/lost.

## Observability and qualification

- WebXR CSV adds `remote_enabled`, `remote_source`, `remote_signal_state`, `remote_sequence`, and locally measured `remote_packet_age_ms` without removing existing current/target or Polar fields. Event rows cover selection, live, stale, recovered, switched, and disconnected transitions. The pre-entry timing readout is session-local and is not copied into per-packet rows. Per-packet logging is forbidden.
- Ordinary affect and placement synchronization do not promise identical Flubber animation phase, random outline offsets, palette, size, or other visual customization. The explicitly invited Party path is different: its returned aggregate scene carries the bounded shared visual state and uses stream-ID-derived deterministic outline offsets so the logical Party reconstruction is consistent across connected browser and Tauri endpoints. A smartphone may apply its untransmitted local camera projection to see more of that same scene.
- Unit and mock tests cover both typed codecs, shared-channel dispatch, cached-sender compatibility, clamping/finite validation, unsigned wraparound, normalized/denormalized/relative placement math, separate rate and liveness ownership, heartbeat/backpressure policy, lifecycle, discovery/selection/switch/teardown, stale/recovery hysteresis, bounded gap diagnostics, and XR input ownership. Static tests retain local-only SDK loading, exact button labels, no automatic page-load connection, no microphone/audio request, wake-lock lifecycle, receiver mode/timing readouts, HUD warning, and additive CSV fields.
- Repeatable browser stress tests may use the explicit `?mock-polar=1` deterministic 130 Hz fixture because it traverses the same bounded metric, desktop smoothing, and broadcaster path. Mock results never substitute for the separate worn-H10 acquisition receipt.
- Research qualification additionally requires current desktop Chromium plus Meta Quest Browser hardware tests: one and two sources, manual and Polar-derived desktop movement, source loss/recovery, direct and TURN routes, congestion without obsolete backlog, a two-minute direct-Wi-Fi soak, and route/RTT/stale/backpressure reporting. Software receipt latency is one receiver XR frame plus no more than one 60 Hz sender scheduling interval, excluding network latency. Missing physical results keep the feature experimental.
