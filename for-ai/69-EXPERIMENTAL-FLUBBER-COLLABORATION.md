# Experimental FLUBBER collaboration

This is the normative contract for Ground Control's reciprocal **Synch with Universe** and multi-source **Invite a FLUBBER** modes plus the Tauri settings WebView's compatible Party host/broadcaster roles. They extend the reviewed 12-byte coordinate transport; they are not chat, accounts, presence storage, experiment recording, physiology exchange, native remote-control authority, or a general networking API.

## Shared boundary

- Loading the page or desktop app constructs no VDO.Ninja client. Each mode starts only from its exact user action and stops on explicit stop, page/app close, or refresh.
- Universe and Party are mutually exclusive with one another and with every ordinary JSON/live send or receive role. They never enter portable settings, browser preferences, CSV, or Experiment state; Experiment start is blocked until collaboration stops.
- Public names, peer-IP visibility, third-party signaling/STUN/TURN, relay latency, and hosted-service availability carry the same disclosures as ordinary remote FLUBBER. Universe sends only bounded final/local-intent X/Y frames. Party guests may additionally provide the ordinary optional normalized viewport-placement frames. The Party host returns a bounded aggregate containing public labels, X/Y, normalized scene positions, relative sizes, stale flags, shared palette/base shape/amplitude/disorder/speed/opacity, and animation phase. No raw pointer trajectory, physiology, metric, timestamp, private participant identity, portable settings object, CSV row, or research state is added.
- Both modes reuse the locally vendored VDO.Ninja SDK and `flubber-remote.js` codec, partial-reliability channel, latest-state backpressure, stale hold, recovery hysteresis, diagnostics, and teardown. Ordinary X/Y and placement retain their 60 Hz cap and 100 ms heartbeat. Aggregate Party scenes are capped separately at 30 Hz with a 250 ms unchanged heartbeat and zero queued backlog. They add no backend, second Party connection, or WebSocket fallback.

## Synch with Universe

- Universe is an explicit paired duplex exception intended for two people. Each named browser simultaneously advertises its own local control intent and discovers other Universe sources, but it excludes its own fresh random stream ID. Each browser selects only one incoming partner; as with every public unauthenticated room, unrelated listeners cannot be cryptographically excluded and must be treated as disclosed observers rather than trusted participants.
- Use public room `affect_tracker_universe_v1`, source prefix `aft_universe_`, label suffix `Universe FLUBBER`, and custom channel `flubberuniversev1`. Discovery never auto-selects: each person explicitly selects the other person's named source.
- Universe does not offer or consume ordinary placement packets. Its one shared displayed object retains local screen placement on each browser; only affect intent is combined.
- A browser is reciprocal-live only after it has received a valid partner coordinate and at least one listener is connected to its outgoing source. Receiving alone reports that it is waiting for the partner to choose back. The radar closes only on reciprocal-live, not on discovery, selection, connecting, or one-way receipt.
- Each browser preserves an independent locally smoothed full-scale intent pair. While reciprocal-live, the one displayed shared Flubber adds the two X intentions and the two Y intentions independently, then saturates each sum to `[-1,1]`; it never averages or halves either person's control. Either participant can therefore reach any axis extreme while the other is neutral, matching-direction inputs reach saturation sooner, and opposing inputs counteract one another. Because addition and saturation are commutative, both browsers converge without assigning a master. Stale holds the latest shared position; it never falls through to unrelated input.
- Universe transmission uses the existing Document Picture-in-Picture frame owner and renewable wake lock. Loss of that foreground helper is visible and recoverable with the same user-gesture restore action. Browser/OS scheduling cannot be overridden; reliable low latency still requires an active foreground frame owner.

## Invite a FLUBBER

- Party is a host-arranged shared scene, not affect co-control. The host's main Flubber and axes stay local. Each invited ordinary public `aft_flubber_` source is rendered as a separate labelled companion using the canonical renderer and only that guest's latest accepted X/Y. Every guest retains its own bounded session-only host position and can be dragged with pointer capture or moved with arrow keys without moving the host or another guest. When that source also provides normalized placement, the first placement anchors to the initial guest location without a jump; later source displacement moves only that guest by the same relative viewport delta. Any host-side guest drag or arrow move reanchors its independent offset. The browser host may wrap first-live admission in its cellular birth transition; the desktop host renders the accepted canonical participant directly and does not claim that presentation transition.
- Once at least one invited receiver exists, the host creates a fresh session-only Party ID and host participant ID. It assembles itself followed by every accepted guest in stable roster order and sends the same version-1 `affect-tracker-party-scene` JSON string through each guest receiver's existing `flubberxyv1` RTC data channel in reverse. The encoded UTF-8 payload is at most 8 KiB, contains 1–9 unique participants with exactly one host, clamps every numeric field, rejects malformed/older frames, and has no wall-clock timestamp. An invited ordinary broadcaster accepts a scene only when its own fresh stream ID appears in that roster, follows one host peer until that scene expires, and clears the scene after two receiver-local seconds without a valid update.
- Every connected browser or Tauri Party stage reconstructs the ordered roster, normalized placement, relative size, stale state, shared visual settings, and relayed animation phase. Canonical projection offsets are deterministically derived from each public session stream ID, so the same participant has the same geometry on every screen before any documented local camera projection. The invited broadcaster's own displayed Flubber adopts its returned Party position, relative size, and appearance while continuing to send only its own ordinary X/Y/placement upstream. A guest never becomes Party host through this reply, cannot invite or arrange other Party Flubbers through it, and does not receive another guest's direct connection; the host is the bounded relay authority.
- Party discovery never auto-selects. After the explicitly selected guest produces its first valid live frame, the radar closes automatically while the persistent roster remains visible. At that success boundary the local Flubber moves to viewport center and enters a deterministic SVG cellular-growth cycle. `partyBudVectorGeometry` defines two sinusoidally perturbed compact scalar fields: the daughter begins as a small weighted deformation on the parent's membrane, grows while moving outward, and marching-squares extraction follows the `0.5` iso-surface as its shared saddle narrows from one closed contour into two. `morphPartyBirthContours` then arc-length resamples and cyclically aligns both extracted loops with the canonical renderer's live 192-point parent and stream-driven guest paths, interpolating every vertex until the temporary and ordinary boundaries coincide. Only then does the wrapper disappear. This one-shot pure-math presentation transition never changes either Flubber's coordinates or transport state. Reduced-motion preference skips the movement and exposes the immediate centered final arrangement. The main Invite action reopens discovery for another guest, so every guest still requires an explicit selection and an independent receiver connection. Invited sources may be individually removed; the persistent Stop action closes discovery and every guest receiver.
- A browser or desktop host supports at most eight invited guests. This is a deliberate CPU, WebRTC-peer, accessibility, and viewport bound—not a claim that VDO.Ninja globally limits the room. Duplicate invitations are idempotent. A stale guest remains visible at its held position and labelled state; it never takes over the local main axes.
- Smartphone layouts expose a Party-only local camera after a shared scene becomes active. One pointer on empty scene space pans, two pointers pinch about their centroid, the semantic range covers zoom `0.5`–`1.6`, and Reset returns to centered zoom `1`. Rendering projects every Party object through that camera and object drags use its inverse. Desktop layouts expose no Party camera, and the camera is never transmitted, persisted, recorded, or allowed to mutate the host-authored scene.
- Affect Tracker Desktop exposes two mutually exclusive explicit roles in the settings WebView. **Host Party and scan** projects its newest Rust snapshot into the host participant, invites ordinary public browser/desktop broadcasters, renders the authoritative aggregate locally, and fans the identical encoded scene to all guests. **Broadcast desktop Flubber** advertises Rust-authoritative current X/Y and a session placement so a browser host can invite it, then renders only newer returned scenes that contain its fresh stream ID. Returned coordinates are presentation-only and cannot invoke `set_target`, change settings/history/markers, or enter LSL. The reciprocal scene expires after two receiver-local seconds; the desktop source remains advertised for a fresh invitation. Stop and page teardown close both possible transports.

- Unit tests cover the ordinary role gate, commutative full-scale saturated Universe coordinates and independent extremes, isolated Universe options without placement, self-exclusion, explicit reciprocal readiness, the 12-byte affect and typed 16-byte placement codecs, bounded reciprocal string dispatch/backpressure, relative normalized placement across unequal viewports, placement/liveness separation, the cellular birth's finite one-contour-to-two-contour topology, exact finite two-contour interpolation into canonical paths, explicit party invitations, aggregate codec validation, identical fan-out, rate/heartbeat bounds, duplicate behavior, the eight-guest bound, smartphone camera projection/inversion, and teardown.
- Static/UI tests cover the browser collaboration buttons, dedicated reduced-motion-safe SVG animations, named radar actions, reciprocal-only Universe dismissal, first-live Party dismissal plus one-shot budding transition and reopen, independent host-side per-guest pointer/keyboard movement, returned-scene rendering, separate guest stage/roster/stop, smartphone-only camera gestures/range/reset, role disabling, experiment exclusion, and no automatic connection. Desktop coverage additionally retains its exact host/broadcast/stop actions, bounded snapshot projection and placement, returned-scene membership/peer/sequence gates, stale expiry, local pinned SDK asset, narrow signaling CSP, privacy disclosure, and no automatic connection.
- Cross-runtime qualification requires fresh real VDO.Ninja endpoints. Test ordinary sender/receiver exclusion; phone-browser-to-browser-desktop and phone-browser-to-Tauri-desktop in both host directions; unequal-viewport drags in every direction; local receiver reanchoring; reciprocal two-browser Universe selection and affect motion without placement coupling; foreground degradation/restoration; one/many Party invitations; agreement of every screen's roster, labels, X/Y, ordering, logical normalized layout, sizes, palette/base shape, deterministic geometry and stale state; guest-to-host-to-all motion; host-arranged movement; phone pinch/range zoom and empty-space pan without wire-coordinate changes; stale/remove/stop behavior; reload-to-idle; and full cleanup of every signal. Tauri tests must additionally prove remote scenes cannot mutate Rust state or LSL and must cover current WebView2, WKWebView, and WebKitGTK before cross-platform release.
